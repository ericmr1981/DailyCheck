## 1. 问题陈述

**谁**：DailyCheck 是多仓零售库存管理系统（当前 8 个仓、5 个用户、多租户 PoC 已就位），正从内部工具走向商业化 SaaS。直接受影响的人有两类——内部运营者（门店/研发/配送中心的一线录入与管理岗）和商业化后的付费租户管理员。

**什么场景**：日常库存作业中，权限被当作"登录与否"和"三级职级"来处理：
- 任何登录成员都能查看**全部报表并导出**，其中包含成本类敏感数据（报表/导出口径对成本零隔离）。
- 同类敏感操作（出库回退、盘点、库存调整、状态跃迁）的守卫级别**不一致**：156 条路由中 82 条有角色守卫、70 条仅要求登录，其中 21 条是写操作。同类操作"抄错邻居"即产生倒挂。
- 订货审批是"DC manager 一刀切"，无法按金额/数量/业务类型分级。
- MCP/Agent 的 token 权限（路径级 ACL + 仓白名单 + 限速）事实上比 Web 侧更细，但两套体系**各自为政**，没有统一词汇表。

**现在怎么解决**：靠代码内联判断 + 20 多处模板字面量硬编码（如 `g.role['role'] in ('manager','admin')`）+ 人工评审。历史上已发生过两次权限事故（品项删除权限倒挂：staff 可删；营业额 API 越权：任意登录可写），当时靠事后补丁 + 4 条测试收尾。

**为什么不行**：当前模型是**单调阶梯**（staff(1) < manager(2) < admin(3)），升一级 = 获得该级全部能力，**做不了加法、做不了减法**。因此"能审批订货但看不到成本价""财务只读全仓报表""审计只看盘点记录""实习生只录入不扣账"这些需求**在现有模型里无法表达**。更糟的是"谁该做什么"没有单一事实来源，只能读代码推断，一致性靠人肉维持——上一次同类事故有明确的复发风险。

**为什么现在做**：商业化在即，多租户是把权限复杂度放大的乘法器（每个租户都要有自己的角色与数据边界）。在引入租户管理员分权之前，必须先有可复用、可审计、可回归的权限词汇表与矩阵作为地基。

## 4. 我们的差异化

**用户为什么选我们，而不是竞品或替代方案**：

1. **库存语义原生 + 权限可精细化**：竞品要么"轻到没权限"（Excel/管家婆），要么"重到改不动"（用友/金蝶需顾问）。DailyCheck 在既有库存/订货业务语义上直接长出细粒度权限，不牺牲易用性。
2. **零迁移的渐进升级**：现有 3 级角色直接映射为 3 个**内置角色包**，绑定关系不变 → 存量 5 用户行为零变化。竞品切换是"推倒重来"，我们是"原地长高"。
3. **单一事实来源的权限矩阵**：把"谁能做 X"从散落代码/模板收敛为一份显式矩阵（文档 + 常量），UI 与守卫共用。竞品里角色能力往往藏在配置里、不可读；我们做到**可反查、可审计、可回归**。
4. **Web 与 Agent 权限同一词汇表**：MCP/Agent 的路径 ACL 与仓白名单引用同一权限点，避免"两套体系各自为政"——这是差异化能力，也是自动化时代的前置优势。
5. **只读/审计/财务内置角色包**：直接回应"报表与成本可见性"痛点，对财务/审计场景开箱即用（对标 Sage/LedgerPine 的行业惯例），无需客户自建。

## 5. 核心功能（RICE 排序）

> RICE：Score = (Reach × Impact × Confidence) / Effort。Reach 1–10（季度受影响用户，1=极少,10=全部）；Impact 0.25/0.5/1/2/3（3=巨大）；Confidence 50%/80%/100%；Effort 1–10（人月）。
> 每条功能已映射 Eric 选定的四个优先痛点（痛点1 报表成本可见性 / 痛点2 敏感操作收紧 / 痛点3 审批分级 / 痛点4 MCP权限）。

| 现有角色 | 映射为内置角色包 | 关键说明 |
|----------|------------------|----------|
| staff | 基础作业包 | 默认不含 `report.cost.view` / `report.export` / 敏感写权限点 |

## 6. MVP 范围

**MVP = 阶段 1「止血 + 地基 + 两大 P0 痛点」**，一个迭代内交付：**F1、F4、F5、F2、F3、F9**。

> 为什么这 6 条同批：它们**共享同一份产物（权限矩阵 / 权限点词汇表）**，且强耦合——F1 是地基，F2/F3 是守卫收敛（依赖 F1 词汇表），F4/F5 是用户价值最高的两个 P0 痛点（报表/成本可见性、敏感操作收紧），F9 是防复发的安全网。拆开交付会重复搬运同一 artifact，不符合"每步可发布、可回滚"的渐进纪律。若必须再切，**最小可发布切片 = F1 + F2 + F9（纪律统一，无行为变化的止血）**，随后 F4/F5 叠加。

**进入阶段 2**（2–3 个迭代）：F8 权限矩阵 UI → F6 审批分级 → F7 MCP 词汇统一。
**进 Backlog**：F10 自定义角色、F11 租户/仓级分权（均在 F9 回归基线 + 多租户全链路租户化之后立项）。
**本期只预留扩展点、不实现**：数据范围字段（self/warehouse/multi-warehouse/tenant）、双人复核（提交人 ≠ 审批人）、审批阈值 schema。

## 7. 明确不做（Out-of-Scope，每条带原因）

| 不做项 | 原因 |
|--------|------|
| 自定义角色即时编辑（DB 驱动 UI 增删） | 属 F10，Backlog；本期内置角色包 + 克隆已覆盖 90% 场景，过早引入会放大误配风险 |

| 字段级权限做到"每个字段一个权限点" | 行业共识是**只对有风险的动作做细粒度**，否则角色数量爆炸、配置人员理解成本飙升；本期只做成本类字段（`report.cost.view`） |

| 单点登录（SSO/SCIM）与 MFA | 商业化安全项，独立于权限粒度；不在本次范围（商业化 P0 清单另有归属） |
| 双人复核（SoD 强制，如盘点提交人≠审批人） | 属 F6 之后的独立项；本期"具两段式雏形"已够用，强制 SoD 需配套审批流改造 |
| 权限热力图 / 动态治理分析 | 属"权限从配置项升级为治理中枢"的远期方向，依赖 F9 埋点与矩阵，最早商业化后期 |
| 前端导航硬编码的全面重写 | 阶段 2 F8 一并处理；本期仅收敛守卫与矩阵，避免一次动 20+ 模板引发大面积回归 |

## 8. 验收标准（EARS 格式关键条目）

> EARS 句型：Ubiquitous（系统应…）/ Event-driven（当…时，系统应…）/ State-driven（当处于…状态时…）/ Unwanted（若…则…）/ Optional（若启用…则…）。验收以"行为可观察、可回归"为准。

**F1 权限矩阵单一事实来源**
- Ubiquitous：系统应存在一份权限矩阵单一事实来源，使得任意一条已注册路由的守卫意图均可从矩阵反查到对应权限点。
- Unwanted：若某条路由的权限点未在矩阵中登记，则系统应判定该实现不合规（由 F9 测试拒绝）。

**F2 守卫收敛**
- Event-driven：当代码库被扫描时，系统应不存在"平台管理员守卫 + 角色守卫"叠加的死装饰器（应为 0 处）。
- Ubiquitous：系统应仅有单一事实来源的平台管理员守卫实现与审计日志实现（各 1 处，替代现有 2 套重复）。

**F3 21 条写操作定级**
- Ubiquitous：系统应为全部"仅登录"写操作提供定级表，逐条给出旧/新行为对照与依据。
- State-driven：当一条写操作被访问时，系统应按其定级后的声明式守卫判定放行或拒绝（不再依赖内联判断）。

**F4 报表/成本可见性**
- Unwanted：若用户不具备 `report.cost.view`，则含成本类字段的报表与导出结果中的该字段应被脱敏（不返回真实值，而非仅前端隐藏）。
- Unwanted：若用户不具备 `report.export`，则导出入口不可用，且导出接口本身拒绝该请求（不可仅靠前端隐藏按钮）。
- Event-driven：当含成本列的数据被导出时，系统应以后端为准执行字段级过滤，且该判定不受前端参数影响。
- Optional：若租户启用了"财务/审计只读"角色包，则该角色可 `report.view` + `report.export`，但在任何写操作上被拒绝。

**F5 敏感操作收紧**
- State-driven：当处于"出库执行/出库回退/盘点审批/库存调整/状态跃迁"任一路径时，系统应要求对应权限点，不得存在"仅登录即可"的写操作。
- Unwanted：若用户不具备 `stock.outbound`，则出库执行应被拒绝；不具备 `stock.outbound.rollback` 则回退应被拒绝（同类操作守卫级别一致）。

**F9 回归基线**
- Ubiquitous：系统应存在"路由 × 角色"全量 deny/allow 基线测试。
- Unwanted：若新增路由未登记权限点，则回归测试应失败（机制化防止权限倒挂复发）。

**F6 审批分级（阶段 2）**
- Event-driven：当订货单金额或数量超过配置阈值时，系统应将其自动上收至更高审批层；阈值内按原层审批。
- Optional：若按业务类型开启分级，则系统应按业务类型适用不同阈值与审批层。

**F7 MCP 词汇统一（阶段 2）**
- Ubiquitous：系统应使 agent token 的路径 ACL 与 Web 守卫引用同一权限点词汇表。
- Unwanted：若 agent token 未授予某权限点，则对应路径的写操作应被拒绝，且拒绝行为与 Web 侧一致。

**F8 权限矩阵 UI（阶段 2）**
- Event-driven：当平台管理员查看某角色时，系统应展示该角色的权限点集合（角色 × 权限点矩阵视图）。
- Unwanted：若角色为内置角色包，则 UI 应禁止直接编辑（需先克隆），避免误改基线。

## 9. 边界条件

| 场景 | 期望行为 |
|------|----------|
| 空状态 | 新租户/新仓无任何角色绑定时，任何写操作均应被拒绝（默认拒绝，非默认放行）；报表视图展示空状态引导 |
| 错误状态 | 权限不足返回明确拒绝（不泄露"存在但无权限"之外的资源信息）；权限点未登记返回"路由未登记"错误 |
| 加载状态 | 权限校验在服务端完成前不渲染敏感字段占位；矩阵视图加载时显示骨架态 |
| 边界值 | 审批阈值（金额/数量）等于阈值时按"≤ 阈值"处理（与思迅/旺店通口径一致），需在定级表显式声明 |
| 并发 | 权限变更与在途请求并发时，以"请求发起点"的权限快照为准，变更后新请求即时生效 |
| 离线 | Agent/自动化在离线重试时，token 权限判定以服务端为准，不缓存越权结果 |
| 权限拒绝 | 拒绝时记录审计（操作人/动作/被拒资源），供审计角色查看 |
| 权限蔓延 | 只读/审计/财务角色被克隆后若被加写权限点，矩阵 UI 应显式告警（对标 NIST view-only 失败模式） |
| 死装饰器叠加 | 若出现"平台管理员 + 角色守卫"叠加，应被视为配置错误并在评审中拦截 |
| 时间边界 | 权限变更时间戳须与租户时区一致（当前系统存在 UTC/CST 不一致历史坑，见 §11） |

## 10. 非功能需求

| 类别 | 要求 | 优先级 |
|------|------|--------|
| 性能 | 权限判定不得显著增加请求耗时；报表/导出字段级过滤在服务端完成，避免全量返回后在端侧丢弃 | P0 |
| 可用性 | 权限服务降级时默认拒绝敏感操作（fail-closed），核心只读流程可降级可用 | P0 |
| 安全 | 权限校验必须在服务端执行；导出与字段脱敏以后端为准；不得仅靠前端隐藏；敏感字段不落审计日志原文 | P0 |
| 兼容性 | 兼容现有浏览器基线；模板导航显隐逻辑改造后保持各角色视图正确 | P0 |
| 可访问性 | 权限矩阵视图键盘可达、对比度达 WCAG 2.1 AA 基本合规 | P2 |
| 国际化 | 权限点命名与角色包名预留 i18n 键，当前仅中文 | P2 |
| 数据埋点 | 权限相关核心事件见 §10.1 | P1 |
| 图标方案 | 权限/角色相关图标统一采用 SVG 图标库，具体库由架构师按项目选型锁定（不预设具体库）；PRD 内一律以文字描述图标含义 | P1 |

### 10.1 数据埋点方案

| 事件类别 | 必埋事件 | 说明 |
|----------|----------|------|
| 获客/激活 | （权限模块不直接涉及，沿用全局） | — |
| 权限拒绝 | `permission_denied` | 记录 `user_id`/`permission_point`/`route`/`tenant_id`；用于发现"无授予但频繁请求"的权限缺口 |
| 敏感操作 | `sensitive_action_executed` | 出库/回退/盘点审批/库存调整/状态跃迁成功事件，含权限点 |
| 导出 | `report_exported` | 含是否成本口径、导出范围；用于审计与异常导出监控 |
| 角色/权限变更 | `role_binding_changed` / `permission_matrix_viewed` | 变更留痕 + 矩阵被查看（治理可见性） |
| 审批 | `order_approval_routed` | 阶段 2 用：含触发的阈值层级与是否上收 |
| 异常 | `error_occurred` | 前端错误 + 权限相关 API 错误 |

> 事件命名规范 `{对象}_{动作}`；属性附带 `user_id`、`tenant_id`、`timestamp`、`device`、`version`。不采集隐私数据（不上报 IP、不存原始输入内容、不记录成本数值本身，只记"是否成本口径"）。

> 注：本项目历史上不依赖重型埋点 SDK（Flask + SQLite 内部工具形态），埋点落地方式（自建轻量封装 vs 现成 SDK）由架构师评估，本 PRD 只定义**事件语义与命名**。

## 11. 已知坑（内嵌）

> `docs/.../memory/pitfalls.jsonl` **不存在**（已确认），故从 `MEMORY.md` 与 Phase 0 盘点文档提取与"权限/角色/用户"相关的已知坑如下。

1. **【历史事故·权限倒挂】** 品项删除权限曾出现倒挂（staff 可删除）；营业额 API 曾越权（任意登录可写）。修复靠事后补丁 + 4 条测试收尾。→ 影响 F3/F9：定级必须成体系、回归必须全量。
2. **【模型缺陷·单调阶梯】** 角色为 staff(1)<manager(2)<admin(3) 单调阶梯，无法做加减法。→ 影响 F1：权限点必须支持"给 staff 加某点 / 给 manager 去某点"。
3. **【死装饰器叠加】** `@require_platform_admin` + `@require_role("manager")` 叠加导致第二个成死代码（如 `items.py:44-45`、`canonical.py`、`forecast.py`、`procurement.py`），读代码者会误判。→ 影响 F2：必须清除。
4. **【双实现】** 平台管理员守卫有 2 套（`require_platform_admin` vs 内联 `_require_admin()`）；审计日志有 2 份（`users.py:830` 与 `agent_tokens.py:184`）。→ 影响 F2。
5. **【UI 散装硬编码】** 模板导航显隐靠 20+ 处字面量判断（`base.html` 内 `g.role['role'] in ('manager','admin')`）。→ 影响 F8；本期不动，避免大面积回归。
6. **【模板陷阱】** `is_rd/is_storefront/is_admin` 只能从 context_processor 取，不能在 `base.html` 的 block 里 set；仓库类型权威来源是 `g.warehouse.warehouse_type`。→ 影响 F8/矩阵视图渲染。
7. **【权限词汇常量位置】** `permissions.py` 已有 `WAREHOUSE_EXEMPT` 等常量；矩阵单一事实来源应落此文件，避免再散。→ 影响 F1。
8. **【master.db schema 纪律】** master.db 变更必须同步 `init_master_db()` 并回归 `tests/test_master_db_migrate.py`；每仓 schema 走幂等 migrate，新增列只进 `migrate_warehouse_db_columns()`，改 ALTER 块需 bump `WAREHOUSE_SCHEMA_VERSION`。→ 影响 F4/F5/F10 若涉及表结构。
9. **【租户闸三道】** 租户隔离为钩子/picker/select 三道，`is_admin` 豁免；跨租户绑定视为脏数据拒绝。→ 影响 F11：分权设计不得破坏三道闸。
10. **【测试基线红线】** 基线为 **18 failed 恒定 pre-existing**（见 `tests/known_failures.txt`），零新增为红线；多数 pytest 须带 `--basetemp=/tmp/pytest-dc`；mcp_server 测试须容器内跑。→ 影响 F9：新增回归须与既有风格一致且不新增失败。
11. **【时区坑】** 生产 CST+8、SQLite `datetime('now')` 为 UTC，时间 bug 在 dev(UTC) 不可复现、生产必现。→ 影响 §9 时间边界与权限变更时间戳。
12. **【MCP 事实更细】** MCP `agent_tokens` 已有路径级读写 ACL + 仓库白名单 + `rate_limit` 列 + 限速（UTC naive 防时区坑），事实上比 Web 侧更细。→ 影响 F7：统一时应以更细的一侧为基准，Web 侧对齐而非反向削弱。
13. **【两段式雏形】** 盘点已具两段式：staff 操作与 admin 审核分离（`stocktake.py`）。→ 影响 F5：收紧时保留该雏形，勿打平。
14. **【订货取消已有矩阵】** 订货取消已实现状态相关权限矩阵（下单人/DC manager/平台管理员三分支，`store_ordering.py`）。→ 影响 F5/F6：作为既有范式复用，勿重造。

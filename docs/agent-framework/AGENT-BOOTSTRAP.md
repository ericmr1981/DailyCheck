> **这份文档是写给 Agent 的，不是写给人的。** 人是审阅者，Agent 是执行者。

## 0. 元指令——开工前先接受这四条

你接到的任务通常是："把这个仓库的开发流程升级成可审计的半自治交付。"

**M1｜禁止一次做完。** 按 §2 的 L1→L4 逐级停靠，每级跑满真实变更才允许升级。这套机制在参考实现里花了 5 天、踩了 7 次有名有姓的坑才成形（其中 2 次是生产事故）；你想在一次会话里做完，等于把 5 天的教训压缩到一次，而且当时没人在旁边看着。

**M2｜禁止跳过自检。** 先跑 §1，用结论决定"最高能到 L 几"。**停在 L2 是合规结果，不是失败。** 能力不够硬上 L4，产出的是一个会在半夜静默写坏数据的系统。

**M3｜每一步的完成判据是一条命令的真实输出**，不是你的判断。没有输出的"已完成"不算完成。

**M4｜四种情况必须停，不许自行绕行：**

| 情况 | 你要做的 |
|---|---|
| 需要生产写操作 | 停，说明要执行什么、影响面、回滚方式，等人点头 |
| 需要注入密钥/token | 停，给出需要哪些凭据、放在哪个路径、权限位多少 |
| 触碰 §8 红线 | 停，写清"这条红线为什么挡住了我" |
| 同一验收命令连续失败 2 次 | 停，贴完整报错；不要试第 3 次 |

**汇报格式**——每完成一步，输出这五行，缺一不可：

```
STEP:      <步骤编号 + 名称>
产物:      <改了/新建了哪些文件>
验收:      <执行的命令>
实际输出:  <真实终端输出，不许概括>
结论:      PASS / FAIL / SKIP（+ 原因）
```

**开工第一句话**应该是 §1 的自检结论，不是"我已经开始施工了"。

## 1. 能力自检（10 分钟，决定你的 L 上限）

逐条跑，把实际输出贴进结论表。**不要凭印象填。**

| ID | 探测项 | 命令 | 判据 |
|---|---|---|---|
| D1 | 仓库可写 | `git remote -v && git push --dry-run origin HEAD` | 有 origin 且 dry-run 不报权限错 |
| D2 | 有 CI | `ls .github/workflows/ \|\| ls .gitlab-ci.yml` | 至少一个能跑测试的 workflow |
| D3 | 测试可跑 | `<测试命令> -q 2>&1 \| tail -20` | 能产出明确 pass/fail 计数（允许有存量失败） |
| D4 | PR 机器可读 | `gh pr view 1 --json body` 或 API 等价调用 | 能读到 PR body 原文 |
| D5 | 可起第二套实例 | 尝试用另一个端口/目录起一份副本 | 能和主实例并存且互不干扰 |
| D6 | 常驻进程 + 可收事件 | `ps` 有常驻 agent？有公网/内网 webhook 入口？ | 两者都在 |
| D7 | 部署可回滚 | 有没有上一个可用版本的产物 + 切换手段 | 能在 < 5 分钟内回到上一版 |

**映射规则（硬判据）：**

```
D1 缺                  → L0（连提交都不行，先修环境，别谈流程）
D1 + D3                → 最高 L1
D1 + D2 + D3 + D4      → 最高 L2
上面 + D5 + D7         → 最高 L3
上面 + D6              → 最高 L4
```

**取你实际满足的最高一级，不要四舍五入。** 并把缺口写成一条待办交给 owner。不要"先搭起来再补"——缺 D7（回滚能力）却上 L3，等于把自动化接在了一个没有刹车的车上。

## 2. 成熟度分级：每一级在挡什么

| 级别 | 新增机制 | 挡住的事故类型 | 依赖 | 停机/资源成本 |
|---|---|---|---|---|
| **L0** | 无 | —— | —— | 0 |
| **L1** | 本地门禁：lint + 失败集基线 + 变异验证 | "自己骗自己"：测试其实早就红了，只是没人跑 | 能跑测试 | 0 |
| **L2** | CI 门禁 + PR 契约（四报告）+ 红线清单 | "合进去才发现坏了"：本地环境与主干不一致 | CI 分钟数 | 每次 PR 几分钟 |
| **L3** | 角色分离（Dev 不 merge）+ 可回滚部署 + 灰度 | "带病上线且退不回来"：事故发现时已经污染数据 | 第二套实例 + 回滚产物 | 双倍实例资源 |
| **L4** | 事件驱动唤醒 + 兜底轮询 + 无人值守闭环 | "人不在就停摆"：所有自动化都要人敲一下才动 | 常驻进程 + webhook | 常驻进程 + 凭据托管 |

### 2.1 升级门槛（硬性，不满足不许升）

| 升级 | 门槛 | 为什么 |
|---|---|---|
| L1 → L2 | 连续 **5 个** PR 未发生基线扩张，且 L1 门禁至少红过 1 次并被人修好 | 没红过的门禁等于没装 |
| L2 → L3 | 有 **1 次**真实回滚演练的成功记录（不是文档，是日志） | 没演练过的回滚等于没有回滚 |
| L3 → L4 | 连续 **10 次**部署在无人干预下完成，含至少 1 次异常自动回滚 | 异常路径没被走过，闭环就是开环 |

### 2.2 什么时候**不该**升级（诚实条款）

- **多人协作、PR 需要人评审业务意图** → 停在 L2。让 Agent 判 merge 会和人的评审职责冲突。
- **变更不可回滚**（数据迁移、对外 API 契约、硬件） → 停在 L2，L3 的自动化只会加快不可逆操作。
- **没有测试** → 停在 L1。门禁再严也只是"没变差"，而"没变差"在零测试的仓库里没有意义。
- **单机、无第二套实例** → 停在 L2，别硬造蓝绿。

停在某一级，就把"为什么停在这"写进仓库的 `docs/<流程文档>`，让下一个人（或下一个 Agent）不要来重新问一遍。

## 3. L1 施工单：本地门禁（半天）

**目标**：任何一次提交，都能在本地明确回答"我有没有让情况变糟"。

### 产物

```
tests/known_failures.txt          基线：当前所有已知失败的清单
scripts/check_known_failures.py   门禁器：失败集 ⊆ 基线
<lint 配置>                         ruff / eslint / gofmt —— 项目现有工具即可
```

### 步骤

**3.1 生成基线。** 跑一次全量测试，把失败项按**稳定标识**（不含耗时、不含路径前缀的可变部分）落盘：

```bash
<测试命令> -q --tb=no 2>&1 \
  | grep -E '^(FAILED|ERROR)' \
  | sed -E 's/ - .*//' \
  | sort -u > tests/known_failures.txt
wc -l tests/known_failures.txt     # 这个数字从此有政治意义
```

参考实现里这个数字是 **23**。你的数字是多少不重要，**它只许变小**才重要。

**3.2 写门禁器。** 逻辑只有三条，不要写复杂：

```python
# scripts/check_known_failures.py 骨架
import subprocess, sys, pathlib

CMD  = ["<测试命令>", "-q", "--tb=no"]   # 例：["python3", "-m", "pytest"]
BASE = pathlib.Path("tests/known_failures.txt")
known = {l.strip() for l in BASE.read_text().splitlines() if l.strip()}

out = subprocess.run(CMD, capture_output=True, text=True).stdout
cur = {l.split(" - ")[0].strip() for l in out.splitlines()
       if l.startswith(("FAILED", "ERROR"))}

new = cur - known          # 新增失败 → 红
fixed = known - cur        # 修好了 → 提示收缩，不阻塞

for t in sorted(new):   print(f"NEW FAILURE: {t}")
for t in sorted(fixed): print(f"FIXED (可收缩基线): {t}")

if new:
    print(f"\n{len(new)} 个新增失败。门禁不过。"); sys.exit(1)
print(f"\n失败集 {len(cur)} ⊆ 基线 {len(known)}，通过。"); sys.exit(0)
```

**3.3 写死"基线只许收缩"。** 在流程文档里加一条红线：**向 `known_failures.txt` 增加行 = 流程违规，必须人拍板**。这条比门禁本身更重要——门禁只是报警器，红线才是锁。参考实现把它列为红线第 1 条。

**3.4 变异验证（最容易漏的一步）。** 新写的测试必须证明它**能变红**：

```bash
# 1. 把修复临时改回 bug 版（注释掉那行 / git stash 局部）
# 2. 跑新测试，必须 FAIL
# 3. 恢复，必须 PASS
```

两个结果都要贴进 PR。**没做过变异验证的测试，按"未验证"处理**——恒真式断言是 Agent 最容易产出的垃圾。

### 验收

```bash
# A. 门禁器能正确放过
python3 scripts/check_known_failures.py; echo "exit=$?"        # 期望 exit=0

# B. 门禁器能正确拦住
#    做法：临时从基线里删掉一行【仍在失败】的用例（即重跑后没有出现在
#    "FIXED" 提示里的那些），重跑，期望 exit=1，然后还原基线。
```

**B 这一步不许跳过。** 没验证过"能红"的门禁，90% 的概率是恒绿。

### 本级别不要做

- 不要建 CI（L2 的事）
- 不要引入覆盖率门禁（存量项目一上来就全红，只会逼人加豁免）
- 不要重构存量失败（那是另一件事，别混进来）

## 4. L2 施工单：CI 契约（一天）

**目标**：让"这个 PR 说清楚了、且没让情况变糟"成为**合并按钮的前置条件**，而不是评审者的记忆负担。

### 产物

```
.github/workflows/ci.yml                      两个 job：test / <项目>-reports
.github/PULL_REQUEST_TEMPLATE.md              PR 契约（三段）
scripts/check_reports.py                      契约门禁器
docs/<流程文档>                                红线清单 + 角色分工
```

### 步骤

**4.1 `test` job = 跑测试 + 零新增门禁。** 关键点：CI 里**不能**用 `|| true`，也不能只跑"改动相关的测试"——必须全量 + 比对基线，否则基线会漂移。

> 现实阻力：全量测试如果超过 30 分钟，你会很想改成"只跑受影响目录"。可以，但必须同时加一条**定时全量**（每日一次），并且明写"这是妥协，不是设计"。基线漂移的代价通常比多跑几分钟高一个数量级。

**4.2 四报告契约。** 不是"写文档"，是**把说清楚变成可检查项**。最小实现只需要检查 4 件事：

| 报告 | 谁填 | 机器怎么判 |
|---|---|---|
| 01 需求对齐 | 人/Dev Agent | PR body 含规定段落标题；段内无未消解占位符 |
| 02 测试 | CI | 失败数 == 0 且门禁 exit == 0 |
| 03 代码质量 | CI | lint 告警 == 0，高危扫描 == 0 |
| 04 部署预演 | CI/Dev | 指定路径下报告文件存在且含签名段 |

**4.3 PR 模板三段**（骨架，直接改）：

```markdown
## 报告 1/4：需求对齐
| ID | 需求 | 状态 |
|----|------|------|
| R-001 | <一句话>（来源：需求 / Issue #N / 生产发现） | <未消解占位符> |

**根因**：
**设计取舍**：
**不在范围（明确排除）**：

## Checklist
- [ ] 报告 01 全部条目已消解
- [ ] lint 0 告警（仅改动文件）
- [ ] 测试零新增失败（对比基线；清单只许收缩）
- [ ] 关键断言经变异验证
- [ ] 触及架构子系统已同步架构文档
- [ ] 未提交运行时文件（db/、logs/、backups/、.venv/）

## 生产侧事项
**变更类别**：<代码 / 依赖 / schema / 配置 / 反代 / 部署脚本 / 纯文档>
**影响子系统**：
**部署时应套用流程的哪些环节**：
**观察窗应重点看什么类别的问题**：
```

**4.4 「生产侧事项」的写法铁律——这是整套机制里最反直觉的一条。**

Dev 只允许写**规范流程粒度**（变更类别 / 影响面 / 前置 / 观察重点），**禁止写针对性操作脚本**（不要"Step 1/2/3"、不要逐条命令）。

理由：部署方（Prod）的价值在于**用自己的视角独立发现问题**。照抄 Dev 的脚本，等于把 Dev 的盲区变成双方的盲区。允许 Dev 声明风险（"此类变更常见失败模式是 X"），那是提示，不是指令。

**4.5 红线清单 + 机器判据。** 见 §8。红线必须写成**可执行的 diff 判据**，不是一句"不许"。文字红线会被 Agent 解释，命令不会。

### 验收

```bash
# A. 故意开一个 body 缺段的 PR（或用 check_reports.py 本地测）
PR_BODY_FILE=/tmp/bad.md python3 scripts/check_reports.py; echo "exit=$?"   # 期望非 0

# B. 补齐后再跑，期望 exit=0
# C. 故意往基线加一行，确认 CI 的 test job 会红
```

**A 和 C 都必须真的红一次。** 记录下那次红的 run 链接，贴在验收单里。

### 本级别不要做

- 不要做自动 merge（L3 的事，而且需要角色分离）
- 不要把 gate 写进 `workflows/*` 之外的地方（比如靠人自觉 review 清单）
- 不要在 PR 模板里放超过 3 个必填段（段数一多，所有人开始敷衍）

## 5. L3 施工单：角色分离 + 可回滚部署

**目标**：让"谁承担生产风险，谁做上线决定"成为结构，而不是默契。

### 5.1 顺序铁律（违反必出事）

```
① 回滚能力   →   ② 部署自动化   →   ③ merge 判定权交给生产端
```

**不许颠倒。** 没有 ① 就做 ②，是在给一个没有刹车的车装油门。参考实现的第一起生产事故就是这一类：切换脚本能跑、能改 upstream 权重，但 `location` 还硬编码指向旧 upstream——切流之后 **30 分钟全站 502**。教训不是"脚本写错了"，而是**"脚本跑通了"和"业务可用了"是两件事**，中间那条缝只能靠终态探活 + 回滚能力来兜。

### 5.2 四件必须自建的东西

| 件 | 要点 | 常见错误 |
|---|---|---|
| **第二套实例** | 独立目录 + 独立端口 + **独立数据库副本** | 只隔离了代码，没隔离数据 → 验证期就写脏了真库 |
| **写隔离开关** | 验证期强制 `DRY_RUN=1`，写操作打日志但不落库 | 只靠"记得别写"；一旦忘记，全站写静默失效但 HTTP 200 |
| **部署单飞锁** | 文件锁 + 会话标识 + TTL（参考：900s）+ 心跳 | 锁没有 session 归属，人工清理时清掉了别人正在用的锁 |
| **回滚脚本** | 一条命令回到上一版，含数据 | 只回代码不回数据 → 回滚后新旧 schema 打架 |

### 5.3 merge 判定不是橡皮章

Prod Agent 的判定动作，四条缺一不可：

1. 确认两个必需 check 全绿（`test` + `reports`）
2. 读 01 报告的「根因 / 取舍 / 不在范围」
3. 用**生产视角**评估：变更类别、影响面、是否有未声明的风险
4. 有异议 → **不 merge**，PR 评论打回 + 开 Issue 转 Dev；无异议 → merge 并按流程部署

merge 权附带的否决权，是这套设计的核心。**没有否决权的"审核"会退化成盖章。**

### 5.4 部署流程的最小形态

```
pull → 起新实例(写隔离) → verify 全项 → 【转正：关写隔离 + 指回真库 + restart】
     → 灰度 5% → 50% → 100%（每档观察） → 观察窗 ≥30min → 收尾
```

三个可量化的点，别省：

- **verify 必须是"全项全绿或全红"**，任一失败即 FAIL 并自动落盘报告（含失败项快照）
- **转正必须在切流之前单独一步**——转正漏掉 = 拿验证态接真实流量
- **观察窗 ≥30min 且要写明看什么**（错误率 / 写失败 / 延迟分位），不是"看着没事"

### 验收

```bash
# A. 回滚演练：从当前版本回上一版，记录耗时（参考实现 < 5 分钟）
# B. 写隔离验证：验证期故意触发一次写操作，确认真库行数不变
# C. 单飞验证：两个会话同时尝试部署，第二个必须被拒（exit != 0 且有明确提示）
```

**B 是这套机制里最值钱的一条验收。** 参考实现因为漏了它，两次同型事故合计 54 分钟静默写失效。

### 本级别不要做

- 不要做无人值守（L4）
- 不要让 Dev Agent 拥有 merge 权（角色会合并，风险判定会消失）
- 不要在还没有演练过回滚的情况下上线

## 6. L4 施工单：闭环（把"人在"这个前提拿掉）

**目标**：从"生产发现问题 → 人开 Issue → 人叫 Dev"变成"事件自己流动"。

### 6.1 唤醒链必须是双通道

```
主通道：webhook / CI 完成事件   → 秒级，但会丢
兜底：  定时轮询（参考：30min）  → 慢，但不会漏
```

**只做主通道 = 事件丢了就永久停摆。只做兜底 = 平均延迟 = 半周期。** 两个都要。

参考实现实测：CI 绿 → merge 完成 = **54 秒**（事件通道）；兜底轮询负责补漏和跨天收敛。

### 6.2 兜底轮询的三条纪律

1. **无变化时静默**：输出 `[SILENT]`，不发消息。否则每 30 分钟一条"一切正常"，人会先关掉它，然后它真的坏了你也不知道。
2. **有退避**：webhook 常常比 CI 完成先到。必须在状态里记 `retry_due`，不能一次判定失败就放弃。
3. **边界归一化**：时间戳、失败计数这类字段，读写两侧的归一化逻辑必须**同源**（同一段代码或同一份常量）。参考实现因为两侧实现不一致，同一批失败被反复重试、反复告警——不是判断错，是"算出下次该重试"这个动作本身被写了两遍。

### 6.3 巡检 Agent（独立于部署 Agent）

| 职责 | SLA | 动作 |
|---|---|---|
| "已解决但仍 open" 的 Issue | ≤ 1 个巡检周期 | 补评论 + 关闭 |
| CI 连续失败的 PR | 每轮 | 汇总输出 |
| 运行中的版本 sha ≠ 期望版本 | 每轮 | 告警 |
| 基线是否被扩张 | 每轮 | 告警（红线） |

**权限边界：能改 Issue 状态（评论、关闭），不能碰代码、CI 和生产。** 它是眼睛和记事本，不是手。

这条边界要写进它的指令里，而不是靠"它应该懂"。巡检 Agent 一旦拿到仓库写权限，它就会开始"顺手修一下"——而它看到的上下文最少，最不该动手。

### 验收

```bash
# A. 拔掉主通道（停 webhook），确认兜底轮询仍能在 1 个周期内收敛
# B. 连续 10 次部署无人干预完成
# C. 注入一次失败（故意让 verify 红），确认自动回滚 + 告警
```

### 本级别不要做

- 不要给巡检 Agent **仓库写权限**（它可以有 Issue 写权限，但不需要、也不该能改代码）
- 不要省掉兜底（"webhook 很稳"是所有事故报告里最常见的第一句话）
- 不要在审批门（危险命令二次确认）还开着的时候做无人值守——**它会在半夜静默卡死**。参考实现踩过：Agent 卡在审批上，整轮不动，而且不报错。

> 用法：每段配一次，之后靠"指针"生效。**权威内容只存仓库文件，提示词只指向文件**——政策改了只改文件，不用重发提示词。

### 7.0 如果只有一个 prompt 的位置（自包含版）

塞进 system prompt 或首条消息。它不装载细节，只负责把 Agent 送到正确的起点。

```markdown
四条铁律：
1. 分级停靠 L1→L4。每级做完停下来等我确认，不许一次做完。
2. 先跑能力自检（文档 §1），用自检结论决定"最高能到 L 几"。
   停在 L2 是合规结果，不是失败。
3. 每一步的完成判据是一条命令的真实输出，不是你的判断。

  STEP / 产物 / 验收命令 / 实际输出 / 结论(PASS|FAIL|SKIP+原因)

现在开始：只跑 §1 能力自检（D1–D7），贴结论表，给出"本仓库能到 L 几"

```

### 7.1 施工 Lead（一次性，跑完即弃）

### 7.2 Dev Agent（常驻）

```markdown
你是 <仓库> 的 Dev Agent。权威口径：docs/agent-framework/workflow.md
（与本文冲突时以 workflow.md 为准）。

你做：开发、测试、提 PR。
你不做：merge、生产环境变更、CI 配置修改。

提交前必须全部满足：
- lint 零告警（仅改动文件）
- 测试失败集 ⊆ tests/known_failures.txt（阈值只许收缩）
- 新增/修改的断言做过变异验证（能变红）
- 触及架构子系统 → 同步架构文档

PR body 必须：三段齐全（报告 1/4 + Checklist + 生产侧事项），
无未消解占位符；「生产侧事项」只写流程粒度，不写操作脚本。

```

### 7.3 Prod Agent（常驻，跑在能碰生产的那台机器上）

```markdown
你是 <仓库> 的 Prod Agent，运行在 <host>。权威口径：docs/agent-framework/workflow.md。

判定：CI 两个必需 check 全绿 → 读报告 01 与「生产侧事项」→ 用生产视角独立评估。
     有异议 → 不 merge，PR 评论打回 + 开 Issue 转 Dev。无异议 → merge。
执行：merge 后按 §5.4 部署：起实例(写隔离) → verify 全项 → 转正 → 灰度 → 观察 → 收尾。
     任一环节异常 → 立即回滚（代码 + 数据），取证后报告 owner。

你不做：改业务代码、改 CI、扩张测试基线、改流程文档自身。

红线（不得自行 merge，报 owner）：<见 §8 六条>

每次动作落盘：谁、何时、对哪个 sha、执行了什么、结果如何。
```

### 7.4 巡检 Agent（常驻，只碰 Issue）

```markdown
每 <N> 小时执行一次巡检。

权限边界：能评论和关闭 Issue；不能改代码、不能改 CI、不能碰生产。
超出这条边界的动作，一律写成建议交给人或 Prod Agent 执行。

检查项：
1. open Issue 中"已解决但未关闭"的（SLA：≤1 个周期）
2. CI 连续失败的 PR（列 sha + 失败 check 名）
3. 生产运行的 sha 与期望版本是否一致
4. tests/known_failures.txt 是否被扩张（红线）

无异常 → 只输出 "[SILENT]"，不发通知。
有异常 → 输出清单 + 建议动作，交给人或 Prod Agent 执行。
```

## 8. 红线：六条 + 机器判据

红线的作用不是"提醒"，是**把不能自动决定的事从 Agent 的决策空间里删掉**。

**两个必须说清的前提：**

1. **命中 ≠ 违规，命中 = 触发人工确认。** 判据只负责把"需要人拍板"的 PR 摘出来；某条命中了但 owner 说"可以"，那就是合法变更。把它当自动拒绝用，红线会很快被改成"永远不命中"。
2. **判据比对的是 `origin/main`（不带三点），不是 `origin/main...HEAD`。** 不带三点会包含**工作区未提交改动**——Agent 本地自检时正是这个状态。CI 里两者等价。表里的 1/2/4/6 均已在参考实现上正反两向实测（注入 → 命中，还原 → 不命中）。

| # | 红线 | 机器判据（照抄可用） | 有输出即命中 |
|---|---|---|---|
| 1 | 扩张测试基线 | `git diff origin/main -- '*known_failures*' \| grep -E '^\+[^+]'` | 新增行原文 |
| 2 | 改 CI / 部署流水线 | `git diff --name-only origin/main \| grep -E '^\.github/workflows/'` | 文件路径 |
| 3 | 改分支保护 / ruleset | 走平台 API，不进 PR diff → 只能靠**动作前自检**：任何 ruleset 写调用先停 | —— |
| 4 | 删除或弱化架构铁律 | `git diff --numstat origin/main -- 'docs/ARCHITECTURE.md' \| awk '$2 > $1 {print "HIT +"$1" -"$2}'` | `HIT +0 -1350` 这类行 |
| 5 | owner 标注"需拍板"的需求 | PR/Issue 标签含 `needs-owner` 或正文含约定标记 | —— |
| 6 | 改流程文档自身 / merge 政策 | `git diff --name-only origin/main \| grep -E 'docs/agent-framework/(workflow\|AGENT-BOOTSTRAP)\.md'` | 文件路径 |

**判据 4 有一个必须知道的合法命中**：文档**瘦身或内容迁移**（把细则搬到 ADR / 别的文件）天然是"删除 > 新增"。这类 PR 会命中，但属于正当变更——判断标准不是行数，而是「删掉的内容去哪了」。所以命中后要看的不是"删了没有"，而是 PR 里有没有写清去向。

**第 6 条是这套机制的免疫系统**：不许 Agent 给自己扩权。没有它，所有其它红线都会在几轮迭代后被"合理化"掉。

**落地建议**：把这六条检查写成 CI 的一个 step（只在 PR 上跑，命中就 `exit 1`，日志里打印"该变更需 owner 拍板"）。**但写这个 step 本身又违反第 2 条**——所以正确顺序是：由 owner 一次性把它加进 workflow，之后 Agent 只读不写。

**更省事的替代**：多数"想加个门禁"的诉求本质是一个断言。写成 `tests/` 里的测试用例，既享受 CI 强制，又不触碰流水线、不触发第 2 条。参考实现有一次就是这么绕开的。

## 9. 失败模式库：参考实现真实踩过的坑

这不是假设清单，每条都对应一次真实事故。护栏栏写的是"现在仓库里怎么防的"。

| # | 症状 | 根因 | 护栏 |
|---|---|---|---|
| 1 | 全站写操作静默失效，HTTP 200，日志只有 WARNING | 验证态（写隔离）的实例被直接切去承接流量 | 转正作为**独立步骤**；切换脚本内置写隔离守卫，未转正拒跑（exit 3） |
| 2 | 部署脚本把"正在承流的实例"原地重启成验证态 | 脚本只挡"切换"，没挡"重启" | 起实例前探活当前流量归属；在役则先切走再重启 |
| 3 | 人工清理部署锁，清掉了另一个会话正在用的锁 | 锁没有会话归属信息 | 锁带 session/token；清理前必须先 `status` 确认归属者已死 |
| 4 | 对齐分支时 `reset --hard` 静默覆盖了未跟踪文件 | git 对"工作区未跟踪 / 目标树已跟踪"的文件直接覆盖，不冲突 | 动 HEAD 前先算路径差集；对齐在独立 worktree 做 |
| 5 | CI 门禁对"补了 PR body"不生效，重跑也没用 | 门禁读的是**事件时刻的 body 快照** | 补完 body 必须推一个空 commit 触发新事件 |
| 6 | 门禁恒红，只因为正文里举了个反例 | 门禁靠字符识别"未消解"，正文里的同款字符也算 | 约定：正文用文字描述（"红叉"），不用符号 |
| 7 | 无人值守时 Agent 卡在危险命令审批，整轮不动且不报错 | 审批请求弹不到人面前，超时后 BLOCKED | 常驻 Agent 的危险操作走"预授权白名单 + 事后审计"，或明确接受"这一步必须有人在" |
| 8 | webhook 比 CI 完成先到，判定失败后再也不重试 | 没有退避重试状态 | 状态里记 `retry_due` + 最大重试；归一化逻辑读写同源 |
| 9 | 文档写的架构和代码不一致，且没人发现 | 手写文档必然腐烂（参考实现实测漂移 **44%**） | 派生文档（机器生成 + CI 校验一致性）；手写文档只放"为什么"，不放"是什么" |
| 10 | 新增的 CI 门禁 PR 被自己的红线挡住 | 改 workflow 命中红线 #2 | **先问能不能用测试表达**——写进 `tests/` 就完全避开红线（详见 §8 末） |

**第 1 条和第 7 条是无人值守的两类失败，方向正好相反**：一类是它会**做错事**（写坏数据，还回 HTTP 200），一类是它**什么都不做**（卡在审批上，整轮不动）。后者更隐蔽——进程活着、日志正常、监控不报警，只是所有需要审批的动作静静躺在队列里。上无人值守之前，先确认你的 Agent 在无人应答时是"跳过"还是"卡死"，这两者要用完全不同的策略。
